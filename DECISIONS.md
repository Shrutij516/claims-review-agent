# DECISIONS

## Decisions

- **D1.** Fresh repo and history, named `claims-review-agent`. The old history contains assessment files and a resume with personal contact info.
- **D2.** Keep Groq `openai/gpt-oss-120b`. Tests use a fake LLM. Eval reports spread over runs.
- **D3.** Flags come from deterministic tools wherever possible. The LLM judges only what rules cannot see (clinical note vs policy text) and writes the explanation. Eval is reported per anomaly type so we can show where the LLM helps and where it does not.
- **D4.** Synthetic data policy: real ICD-10-CM codes (public), real CPT code numbers but descriptions are our own words (CPT text is AMA copyrighted), a few HCPCS Level II codes. All policies, price bands and unit limits are invented and labeled SYNTHETIC.
- **D5.** Eval split: 60 claims, 20 dev and 40 test. Test is frozen by SHA256 in `data/v2/TEST_SPLIT.sha256`. Never tune on test. Changing test data needs a hash update plus a new Decisions entry.
- **D6.** Policies have stable ids (POL-001) and numbered criteria (POL-001.2) so every decision can cite evidence precisely.
- **D7.** Data is produced by a seeded generator (seed 42) into plain JSON. No database.
- **D8.** v1 data and baseline stay untouched until the Phase 2 baseline replaces them.
- **D9.** Python is managed by uv (`.venv`, Python 3.12) because Homebrew python@3.12 3.12.13_2 fails at ensurepip (pyexpat symbol mismatch with macOS libexpat).
- **D10.** Phase 1 deviations accepted: code tables are objects with a note field plus a codes list; `flag_catalog.json` has a parameters block (price bands, unit limits, tiers, windows) and a synthetic_notice; HCPCS J codes sit in the claim `cpt` field; `--freeze` is the only way to write `TEST_SPLIT.sha256`; the generator re-derives every R_ flag from the catalog and fails on mismatch.
- **D11.** Retrieval is BM25 (`rank_bm25`) over one chunk per numbered policy criterion (id like POL-003.2). Deterministic, free, easy to explain, and every hit is directly citable.
- **D12.** Tools are pure typed functions with no LLM. The rule checks are implemented independently of the generator's check, so agreement on all 60 claims is a real cross-check. If they disagree, one implementation or one label is wrong: investigate and log it, never edit a label just to pass.
- **D13.** A claim whose processing fails is counted as an error, never dropped. In metrics an error counts as wrong (an error on an anomalous claim is a false negative, on a clean claim a false positive) and is reported separately.
- **D14.** Tuning protocol: tools, retrieval and prompts are tuned on dev only. The test split is run only in Phase 6, behind an explicit `--final` flag.
- **D15.** v1 files (`src/rules.py`, `src/baseline.py`, `src/generate_claims.py`, `data/claims.json`, `data/ground_truth.json`, `tests/test_baseline.py`) are retired at the end of this phase in a separate commit, once the new baseline exists.
- **D16.** Known simplification: one CPT per claim. Real claims have several lines. Listed as a README limitation.
- **D17.** (Claude Code, Phase 2) Rule flag evidence uses criterion ids from a static map in `src/claims_review/rules.py` (`policy_criteria_for`), because the catalog lists policy ids only. A test checks that every mapped criterion exists and belongs to a policy the catalog lists for that flag.
- **D18.** (Claude Code, Phase 2) Retrieval indexes the policy title together with the criterion text, lowercases alphanumeric tokens, drops a short fixed stopword list, and returns only positive-score hits. These choices were fixed before any retrieval metric was computed.
- **D19.** (Claude Code, Phase 2) A claim with an empty ICD-10 list is a parse error. If the procedure code is not in the tables, only R_INVALID_CODE is returned, because every other check depends on the procedure. The scripts use only the chosen split's claims, including as the cross-claim store, so dev runs never read test claims.
- **D20.** (Claude Code, Phase 2) `rank_bm25` and its dependency numpy were installed from the package index. That was the only network use in Phase 2.
- **D21.** Retrieval unit changed from top-3 criteria to top-2 whole policies, passed in full to the LLM in Phase 3, with an optional flag-aware query chosen by the pre-registered rule in `scripts/eval_retrieval.py` (use the flag-aware query only if its policy recall@2 on dev is strictly higher than the plain query). Reason: policies have 3 to 5 criteria; criterion-level top-3 dropped sibling criteria (dev micro recall@3 was 0.571) and duplicate-claim policies are not findable from claim text. The citation checker still requires exact criterion ids from the returned text. This was chosen after seeing dev metrics, on dev only.
- **D22.** The rules-only baseline is at the ceiling for rule-type anomalies by construction (rules and labels share one catalog), so its numbers show consistency, not real-world accuracy. On dev it got TP=7 FP=0 TN=11 FN=2 and both misses are the policy-reading anomalies (V2-0009, V2-0053). By the same construction its test recall can be at most 12 of 18. The comparison with the agent is only meaningful on the policy-reading cases.
- **D23.** The README must state that rules and labels derive from one catalog and that labels are single-author.
- **D24.** Known limitations to list in the README: laterality evidence accepts any diagnosis that names a side regardless of body site; the E/M level check silently passes when no diagnosis is in the tier table; one CPT per claim (D16); policy criteria must be one line each. Also: the POL-002.4 citation uses tier 1 as a stand-in for "routine or minor illness" (D27); the V2-0031 evidence mismatch (D28).
- **D25.** (Claude Code, Phase 2b) Outcome of the D21 selection rule on dev (`results/retrieval_dev.json`): policy recall@2 was 10 of 12 for the plain query and 11 of 12 for the flag-aware query, so the flag-aware query is selected. The difference is one claim (V2-0052, a rule-flagged duplicate) out of 12, and the flag text helps there by construction, because the flag description is what points to POL-004. Policy recall@2 is micro: gold policy ids found divided by gold policy ids, summed over claims. Criterion coverage is the share of gold criterion ids that sit inside the returned policies.
- **D26.** (Claude Code, Phase 2b) Smaller choices: `parse_claim` now rejects a billed amount of exactly 0 (it was accepted; units below 1 were already rejected); `eval_retrieval.py` now saves `results/retrieval_<split>.json`, while `run_baseline.py` does not save results yet; `scripts/check_evidence.py` compares evidence at policy level and at criterion level; whole policies list their criteria in numeric order.
- **D27.** R_EM_LEVEL_VS_DX also cites POL-002.4 when the best diagnosis tier is 1 and the code is 99214 or 99215. Reason: POL-002.4 names both levels. The labels for V2-0007 and V2-0011 were right and the rules were incomplete. The V2-0051 label (dev) was incomplete and is corrected under D5: one policy entry, POL-002.4, added to its evidence. The test hash is unchanged and verified (the hash covers only test-split claims and their ground truth, and V2-0051 is dev). Approximation: tier 1 stands in for "routine or minor" (see D24). (Claude Code addition: the generator's hard-coded evidence for V2-0051 in `src/generate_claims_v2.py` was changed the same way, so the generated files stay byte-equal to the committed ones. `--freeze` was not run.)
- **D28.** V2-0031 evidence mismatch left as is. The label cites POL-007.2 (documented 40 mg = 4 units, billed 12); the rule checks only the unit limit and cites POL-005.1 and POL-007.3. The README must list this as a known limitation. Phase 6 scores evidence on rule-derived criteria and does not penalize extra valid citations.
- **D29.** The agent is a fixed LangGraph state machine (parse, rules, retrieve, judge, verify, explain, finalize) with two validated LLM calls, not a free tool loop. Reason: auditable, deterministic where possible, testable with a fake LLM. The human review pause and SQLite checkpointer are Phase 3b.
- **D30.** LLM access goes through the groq SDK behind a small interface; temperature 0; the model comes from GROQ_MODEL, default openai/gpt-oss-120b; tests use a fake and make no network calls; JSON is parsed and validated in plain Python (no new validation dependency).
- **D31.** Citation rules. A judged flag is accepted only if its flag_id is a policy_reading flag in the catalog, its criterion id is in the retrieved text, and its quote is a verbatim substring of the note (whitespace collapsed). Explanations may cite only verified criterion ids; one retry, then a deterministic template. All rejections are kept in the result and trace.
- **D32.** Failure handling. The judge gets one retry. If it still fails, rule flags are kept and the result is "needs_human_review" or "flag", never "pass". Parse errors skip the LLM. In evaluation, llm_failed and parse_error count as errors (D13).
- **D33.** New evidence kind "note" (id is the quoted text) added for judged flags. `models.py` does not validate evidence kinds, so it was not changed. Dependencies added: langgraph, groq.
- **D34.** (Claude Code, Phase 3a) Smaller choices, none tuned on any metric: the judge prompt also shows the procedure and diagnosis labels and the modifiers, and asks about both policy_reading flags for every claim; explanation_source is "fixed" for the no-LLM texts (no issues, judge failed, parse error); when the judge failed but rule flags exist, the explanation gets a sentence saying policy reading failed; `template_explanation` replaces any criterion id in a flag detail that is not in that flag's policy evidence with "[unverified id]"; the judge reply may be wrapped in one markdown code fence; an exception from the LLM call counts as a failed attempt; explanation retries and fallbacks are recorded in errors while status stays "ok"; the 120 word limit is in the prompt only, not enforced in code; results carry no timestamps or latency, so identical inputs give identical results; `review_claim.py` reads GROQ_API_KEY from the environment only; prompt builders live in `src/claims_review/prompts.py`.
- **D35.** Human review pauses the LangGraph with interrupt() after the agent result. Actions: approve, override, request_info. approve only when the agent recommended pass or flag; override needs a decision (pass or flag) and a reason; request_info needs a question and ends the review as needs_info. Every action records reviewer name and a UTC timestamp.
- **D36.** Pauses persist in SQLite (`runs/checkpoints.sqlite`, gitignored) with thread_id equal to the claim_id, one review per claim. Resuming re-runs no LLM call and survives a process restart (tested with a second saver on the same file).
- **D37.** Human review is opt-in (`human_review=True`). The Phase 6 eval uses the plain agent so the metrics measure the agent, not the reviewer.
- **D38.** Hardening after the live smoke run: a judged flag's criterion must belong to a policy the catalog links to that flag; explanations may not use decision words or bare policy ids; the explainer prompt now says a human decides and to use only given facts. Limits that remain and go in the README: verification proves grounding (the quote is in the note, the criterion is in the retrieved text), not that the quote supports the flag; a note could contain instructions that suppress a policy-reading flag; an explanation can still mention codes or numbers that are not in the evidence.
- **D39.** Dev smoke run, not a metric: V2-0009, V2-0053 and V2-0005 run live through GroqLLM. The flags were correct and verified, the clean claim passed, and no metric was computed.
- **D40.** (Claude Code, Phase 3b) Smaller choices: all graph state is now plain dicts and lists in both modes (nodes rebuild ParsedClaim, Flag and PolicyHit when needed), so checkpoints need no custom serialization; results and the 3a tests are unchanged; `build_graph` has one extra argument, `clock`, for the record timestamp; the `agent_result` inside the final record has its trace extended with the human_review and record entries; for approve, `final_decision` is the agent's recommendation, and for request_info it is None; the reviewer name is stripped; request_info is allowed even when the agent needs a human; `get_review` can also return "incomplete" for a thread that has a checkpoint but is neither waiting nor finished; `submit_review` on a thread that is not waiting raises ReviewActionError; `start_review` needs a string claim_id, but an unparseable claim that has one can be reviewed; `template_explanation` also removes decision words and bare policy ids from flag details; the `show` and `submit` script commands load no claims and use --split only for the test guard; a relative --db is resolved against the repo root; the template-explanation test reads only dev claims. I36 says "a code check": that means the decision-word and bare-policy-id checks in `check_explanation`. No check for ICD or CPT codes that are missing from the evidence was added. One throwaway SQLite probe file for a negative control was written under the system temp directory instead of the scratchpad, and deleted straight away.
- **D41.** The API serves the dev split only; test-split claims are unreachable through it (same message as an unknown id), so the demo cannot leak the frozen split. The Phase 6 eval uses scripts with --final.
- **D42.** The API never returns ground-truth fields (tested at every endpoint) so the UI cannot show the answer key.
- **D43.** One SQLite saver per request, opened and closed in a try/finally, instead of a global connection.
- **D44.** POST /review is synchronous (about 10 seconds with the real model). No background jobs: the UI shows a spinner. A kill mid-run can leave a thread "incomplete" until `runs/checkpoints.sqlite` is deleted (known limitation).
- **D45.** get_review and start_review return agent_result (with the trace) while a review is paused, because the UI needs the trace and the pause payload has none.
- **D46.** Known limitations for the README: the reviewer name is free text (no authentication); no locking if two submits arrive at once for the same claim; the API serves dev claims only.
- **D47.** (Claude Code, Phase 4) Smaller choices: the not-found body is the fixed text "Claim not found." with no claim id in it, so a test-split id and an unknown id give identical bodies; the ground truth file is read at startup only to choose the dev claims and nothing from it is kept; every field of the action body is optional in the pydantic model, so a missing reviewer or reason comes back as the same `{"problems": [...]}` 422 as any other action problem, while an unknown extra field gets FastAPI's standard 422; the action endpoint returns 409 when no review is awaiting (not started, completed or incomplete) before it validates the action; the start endpoint checks for an existing review before it calls the LLM factory, so an existing review gives 409 even if the key is missing, and it still maps a ReviewExistsError from the race case to 409; endpoints are plain `def` functions, so FastAPI runs them in a thread pool and the slow start does not block other requests; a relative `db_path` is resolved against the repo root, as in the scripts; `clock` is passed to submit_review as its `now`; GET /claims calls get_review once per claim (20 per request) on one saver; the "split" key in the /health response is the server's configured split, not a ground-truth field, so the no-ground-truth-keys test covers every endpoint except /health; the CORS test also checks that credentials are not allowed; the default `llm_factory` is the `GroqLLM` class itself, built only when a review starts; tests count factory calls to prove reads and repeat starts never build an LLM. The `runs/checkpoints.sqlite` file Claude Code found was the reviewer's own demo file from `scripts/human_review.py` runs, not a test leftover; Claude Code deleted it without asking (I40). After deleting `runs/`, a full test run did not recreate it, so the test suite does not write to the default path.
- **D48.** The UI is React + Vite + TypeScript in `ui/`, with plain CSS and no component library, router or state library. Reason: fewest dependencies, every line readable.
- **D49.** Evidence is checkable in the UI: the model's note quote is highlighted inside the clinical note and criterion text loads on demand, because a reviewer must be able to verify a citation, not just see its id.
- **D50.** The UI never decides anything. Every action goes through the API; client-side checks are hints and the server is authoritative.
- **D51.** New read-only endpoint GET /criteria/{id} returns criterion text (policy text only, no ground truth).
- **D52.** Known limitations for the README: the UI is a demo for the dev split only; no authentication; no polling or live updates; the reviewer name is free text.
- **D53.** (Claude Code, Phase 5) Smaller choices: the session was opened in an older, unrelated project folder (HEAD 6269c21), so Claude Code worked in the sibling `claims-review-agent` repo, which was clean at 9870a45; - **D54.** Eval metrics. Decision accuracy: a claim counts as Flagged when the agent recommends flag, Clear when it recommends pass, and Error when its status is not ok (llm_failed, parse_error, or an exception in the run); an Error counts as wrong (D13) and the error count is reported. Flag precision and recall are micro over (claim, flag id) pairs, so every flag counts equally; an error claim raises no flag, so its expected flags are misses. Zero denominators give "undefined" (null), never 0. Also reported per run: judge flags rejected by verification, LLM retries used, and template-explanation fallbacks. Reason: decision accuracy answers "did it route the claim right", flag scores answer "did it say the right thing", and a null is honest where a 0 would look like a measured failure.
- **D55.** Precision and recall are also reported for policy_reading flags only and for rule flags only, chosen by the catalog's detection field. Reason: rule flags come from deterministic code that shares a catalog with the labels (D22), so they are near ceiling by construction; only the policy_reading flags measure what the LLM adds. Mixing them would hide the LLM's real score behind easy rule hits.
- **D56.** Three runs by default, reported as mean and min to max, with every per-run number saved. Reason: the model call can change over time (I1, I37); reporting the spread instead of the best run is the fix for I1, and three runs is the smallest count that shows a range at an affordable cost.
- **D57.** One-time test guard. The test split needs --final, the output must be `results/eval_test.json`, the run is refused if that file already exists, and the test-split hash must match `data/v2/TEST_SPLIT.sha256` (read only, never written). The final file is opened in exclusive-create mode. Reason: one look at test, on exactly the frozen data, so the reported test number cannot be the best of several tries.
- **D58.** (Claude Code, Phase 6a) Smaller choices: the hash check recomputes the generator's payload (test-split claims plus their ground truth, sorted, compact JSON), not a hash of the claim ids alone as the phase prompt said, because that is what the frozen file holds and an ids-only hash could never match it; the code is in `src/claims_review/evaluation.py` and a test checks it equals the generator's function on a synthetic fixture; an llm_failed claim is an Error at flag level too, so the rule flags it kept are not credited (consistent with D32 and D54); a flag id unknown to the catalog counts in the overall flag scores and in neither subset; the rules-only baseline is scored with the same functions and saved under `rules_only_baseline` with the label "at ceiling by construction (D22)" (label replaced by D60); `--final` on the dev split is refused; the cheap guards run before any data file is read, and on refusal no LLM is built; a missing GROQ_API_KEY stops the run before any claim; besides the per-claim progress lines the script prints one header line and the saved path; `GroqLLM` now has a `temperature` class attribute (0) that `complete` uses, so the results file records it; `git_commit` gets a `+dirty` suffix when the tree has changes; undefined values are left out of the mean and range and `n_defined` says how many runs had a value. No eval was run in this phase (no live LLM calls), so `results/eval_dev.json` does not exist yet.
- **D59.** V2-0033 (dev, CPT 29881, ICD M17.11, note "Right knee pain and swelling. Arthroscopy was performed under regional anesthesia and tolerated well.") got a false positive P_DEGENERATIVE_ONLY in all 3 dev runs (policy_reading precision 0.667, recall 1.0; rule flags perfect; decision accuracy 1.0; 0 errors; 0 rejected; retries 1 to 2). The label is correct: the note describes no degenerative finding, and the osteoarthritis comes only from the diagnosis code, which R_DX_NOT_SUPPORTING already flags. The judge quoted "Right knee pain and swelling.", a real sentence that does not support the flag, so verification passed it, and the explanation then says the note documents osteoarthritis, which it does not. Decision: left unfixed and reported as a measured failure. Reasons: dev is the same 20 claims the agent was built around, so a prompt change that fixes one claim cannot be validated; a general rule "the quote must state the finding" would break absence flags such as P_NO_CONSERVATIVE_THERAPY, where the finding is something the note lacks; a per-flag quote rule would need a catalog change, and the catalog and labels are frozen (D23). README limitation: verification proves the quote is in the note and the criterion is in the policy, not that the quote supports the flag.
- **D60.** The rules-only baseline label is now "rules only, no LLM. Rule-flag scores are at ceiling by construction (D22); it cannot raise policy_reading flags, so its decision accuracy and flag recall are lower." Reason: on the first dev run the baseline scored decision accuracy 0.9 and flag recall 0.78, so the old label "at ceiling by construction (D22)" was true only for the rule-flag scores and misleading for the whole block. A test checks the exact label in the build_output baseline block.
